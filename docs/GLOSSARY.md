# Glossary

Domain-specific terms used throughout DataProof documentation and code. All contributors should use these definitions consistently.

---

## Sample

A discrete unit of material, substance, or subject being analyzed. Examples:
- A blood draw from a patient
- A soil core from a field site
- A chemical batch from a production run
- A water sample from a monitoring station

Each sample has a unique identifier (`sample_id`) and may have multiple measurements taken at different times or under different conditions.

---

## Measurement

A single observed value for a specific metric at a specific time for a specific sample. Measurements are stored in **long-format**:

```
sample_id | timestamp | metric    | value | unit
S001      | 2026-07-02T10:00:00Z | temp  | 22.5 | °C
S001      | 2026-07-02T10:00:00Z | pH    | 7.2  | pH
```

Measurements are the atomic unit of data in DataProof. All analysis packs operate on collections of measurements.

---

## Analysis Pack

A pluggable, domain-specific module that computes derived values from raw measurements. Analysis packs are **pure Python functions** with no LLM dependencies.

**Responsibilities**:
- Compute ratios (e.g., ratio of metric A to metric B)
- Compute aggregations (e.g., mean, std dev, percentiles)
- Compute time-series derivatives (e.g., rate of change)
- Return structured results with citations to source measurements

**Examples**:
- `water_quality_pack`: Computes turbidity ratios, pH stability metrics
- `blood_panel_pack`: Computes cholesterol ratios, enzyme activity rates
- `soil_composition_pack`: Computes nutrient density, moisture retention curves

**Key Property**: Analysis packs are **deterministic**. Same input → same output, always. This is enforced by the trust guarantee (see ADR-002).

---

## Proxy (Derived Ratio)

A computed value derived from one or more measurements. Proxies are the output of analysis packs and the input to LLM interpretation.

**Examples**:
- `cholesterol_ratio = total_cholesterol / HDL`
- `turbidity_index = (turbidity_t1 - turbidity_t0) / time_delta`
- `moisture_retention = water_held / dry_weight`

Proxies are **never computed by the LLM**. They are always computed by deterministic Python code in analysis packs.

---

## Sniffing

The process of automatically detecting the structure of uploaded tabular data (CSV/XLSX). Sniffing heuristics identify:

- **Column types**: timestamp, numeric value, categorical, identifier
- **Units**: °C, mg/L, pH, etc. (from column headers or data patterns)
- **Sample IDs**: Columns that uniquely identify samples
- **Time columns**: Columns containing timestamps or sequence numbers

Sniffing is imperfect and always followed by a **column mapping** step where the user confirms or corrects the detected schema.

---

## Column Mapping

The user-confirmed assignment of uploaded columns to semantic roles. After sniffing proposes a mapping, the user reviews and adjusts it in the UI.

**Example**:
```
Uploaded Column  →  Semantic Role
"Date/Time"      →  timestamp
"Temp (°C)"      →  metric: temperature, unit: °C
"Sample #"       →  sample_id
"pH Reading"     →  metric: pH, unit: pH
```

Column mapping is stored in the `measurement_schemas` table and used to transform wide-format uploads into long-format measurements.

---

## Interpretation Result

The narrative text generated by the LLM (DeepSeek) based on computed analysis results. Interpretation results include:

- **Narrative**: Human-readable explanation of findings
- **Citations**: Inline references to specific computed values (e.g., "[cholesterol_ratio = 4.2]")
- **Confidence**: LLM's self-assessed certainty (used for UI display, not validation)

Interpretation results are stored in the `interpretations` table and linked to the analysis results they reference.

---

## Citation Validation

The process of verifying that every claim in an LLM-generated narrative references a computed value from the analysis results.

**Validation Rules**:
1. Every numeric claim must cite a specific proxy or measurement
2. Cited values must match computed values exactly (within floating-point tolerance)
3. No hallucinated numbers (values not present in analysis results)
4. Citations must be unambiguous (clear reference to source)

**Failure Handling**:
If citation validation fails, the narrative is rejected and the LLM is prompted to regenerate with stricter citation requirements.

**Why This Matters**:
Citation validation is the final enforcement mechanism for the trust guarantee. It ensures the LLM cannot invent numbers or misrepresent computed results.

---

## Watermark Tier

A classification of data quality or trustworthiness, used to flag measurements or analysis results that may require human review.

**Tiers**:
- **Tier 1 (Verified)**: Data from calibrated instruments, validated analysis packs
- **Tier 2 (Provisional)**: Data from uncalibrated instruments, experimental analysis packs
- **Tier 3 (Flagged)**: Data with known quality issues, outlier measurements

Watermark tiers are displayed in reports to help users assess confidence in results. They are **not** used to filter or exclude data automatically — that decision is left to the user.

---

## Trust Guarantee

DataProof's core architectural principle: **deterministic computation is never delegated to the LLM**. All math is done in Python (analysis packs), and the LLM only interprets pre-computed results with citation validation.

See: ADR-002, ARCHITECTURE.md

---

## Long-Format vs Wide-Format

**Long-format** (used in database):
```
sample_id | timestamp | metric | value
S001      | t0        | temp   | 20.5
S001      | t1        | temp   | 21.3
```

**Wide-format** (used in CSV uploads, UI display):
```
sample_id | temp_t0 | temp_t1
S001      | 20.5    | 21.3
```

DataProof stores data in long-format for flexibility and query efficiency, but accepts uploads and displays results in wide-format for human readability.

See: ADR-000

---

## Analysis Result

The structured output of an analysis pack, containing:
- **Computed values**: Dict of proxy name → value
- **Timestamps**: When each computation was performed
- **Citations**: References to source measurements used
- **Metadata**: Analysis pack version, parameters, execution time

Analysis results are stored in the `analysis_results` table and serve as the input to LLM interpretation.

---

## Project

A top-level container in DataProof representing a complete analysis workflow for a dataset. A project contains:
- Uploaded files (stored in MinIO)
- Column mappings (stored in `measurement_schemas`)
- Measurements (stored in `measurements` table)
- Analysis results (stored in `analysis_results` table)
- Interpretation results (stored in `interpretations` table)
- Generated charts and reports (stored in MinIO)

Projects are the unit of organization for users and will be the basis of multi-tenancy in Phase 6.
